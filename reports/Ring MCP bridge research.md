# Bridging Ring to any AI agent

Access to Ring doorbells, cameras, and Ring Alarm now splits cleanly into two worlds that a single MCP bridge must straddle. The **official Ring Partner API** (`api.amazonvision.com`), launched in 2026 under the "Ring Developer Experience" program, is a sanctioned, OAuth-authenticated, webhook-driven surface that is overwhelmingly **read-and-observe**: device discovery, read-only settings, motion/ding/lifecycle webhooks, event history, watermarked snapshots and clips, and short (30–60s) live video — with **no alarm arm/disarm, no siren, lights, locks, intercom, two-way audio, or settings writes** of any kind ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html); [Developer FAQ Q8](https://developer.amazon.com/docs/ring/developer-faq.html)). The **unofficial community APIs** (`ring-client-api`, `python-ring-doorbell`, and the ring-mqtt/homebridge/Scrypted ecosystems built on them) impersonate the Ring Android app against `api.ring.com` and a location websocket, and are the **only** way to arm/disarm Ring Alarm, sound sirens, unlock locks and intercoms, control smart lighting, read live alarm-panel state, and run ~10-minute streams — at the cost of fragile reverse-engineered auth, periodic Cloudflare-WAF `406` blocks, and clear tension with Ring's Terms of Service ([ring-client-api location.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L360-L376); [dgreif/ring #1717](https://github.com/dgreif/ring/issues/1717); [Ring Terms §2(h)](https://ring.com/terms)). No mature Ring MCP server exists today; the handful that do are stale, WIP, or read-only ≤4-star projects. MCP itself, at revision 2026-07-28, has **no native "wake the agent" event push** that works across clients, so event ingestion must rest on a durable server-side log and a polled cursor tool, with host-specific webhook/channel adapters layered on top ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)). The strategic implication is a **hybrid bridge with per-backend capability flags**: official API for sanctioned reads/events/video where possible, unofficial path for alarm and device control, a safety model that enforces confirmation and PINs server-side because Ring enforces none, and home/residential hosting because both backends dislike datacenter IPs. The notes also surface a cluster of **directly conflicting facts** — the program's launch date, the private-app account cap and geography, control scope, and several protocol details — that this report flags rather than resolves.

## The official Ring Partner API is a sanctioned read-and-observe surface with hard limits

An official, public third-party Ring API now exists for the first time. The program is the **Ring Developer Experience**, the marketplace is the **Ring Appstore**, and the API is the **Ring Partner API** (also "Amazon Vision API") at base host `https://api.amazonvision.com`, with authentication at Ring's own OAuth server `https://oauth.ring.com` ([Get Started](https://developer.amazon.com/docs/ring/get-started.html); [API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). Authentication issues user-scoped Bearer tokens that last about **4 hours**, with refresh tokens lasting about **30 days** that **rotate and invalidate the prior token on every refresh**, so a bridge must persist the token as mutable state and refresh on a schedule (~24h recommended) ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html); [Release Notes Oct 22, 2026](https://developer.amazon.com/docs/ring/release-notes.html)). Two linking methods exist: a default **Ring-driven one-way flow** where Ring POSTs an auth code to the partner's Token Exchange URL and the user signs in on a partner-hosted Account Link page, and an invite-only **Partner-Initiated OAuth 2.0 + PKCE** flow (free apps only) ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html); [Developer FAQ Q1–Q3](https://developer.amazon.com/docs/ring/developer-faq.html)). All calls are **server-to-server only** — browser-initiated requests are blocked by CORS, every request needs `User-Agent` and `Hardware_Id` headers, and **datacenter/cloud-hosting egress IPs can receive WAF `406` responses** unless the static egress IP is allowlisted by Ring support ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)).

The capability surface is almost entirely observational. Documented endpoints cover device discovery (`GET /v1/devices` with status, capabilities, coarse country/state location, and read-only configurations including `e2e_encryption.enabled`), per-device event history, WHEP/WebRTC or RTSPS live video (receive-only, capped at **30s on battery, 60s on line power**), MP4 clip download (up to 15 min, only if a recording already exists), JPEG/PNG snapshots, and subscription status ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). All media carries a **mandatory, unremovable visible watermark** (Ring logo, device ID, app name, timestamp) since June 8, 2026 ([Release Notes](https://developer.amazon.com/docs/ring/release-notes.html)). Events arrive by **HTTPS webhook push** to one partner-wide URL, as HMAC-SHA256-signed JSON:API envelopes that must be acked within 5 seconds, with 6 retries over ~1h12m then a 72-hour dead-letter queue; the only pull alternative is the Event History API ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). The rate limit is **100 TPS per client_id**, with semantic versioning and 12-month backward compatibility promised ([Get Started FAQ](https://developer.amazon.com/docs/ring/get-started.html)).

What is **absent** is decisive for this project. The official-platform note, which read the API reference in depth, found no endpoint or scope for **Ring Alarm security modes, arm/disarm, keypad or base station**, no siren, floodlight/spotlight or smart-lighting control, no locks, intercom or garage control, no two-way audio, and **no settings writes of any kind** ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html); [Developer FAQ Q8](https://developer.amazon.com/docs/ring/developer-faq.html); [Program Requirements §2.19–2.20](https://developer.amazon.com/docs/ring/program-requirements.html)). The only "actuation" in the entire official API is playing a sound on a Chime, and that only in Early Access ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). Ring sensors (contact, flood/freeze, temp/humidity, air quality) and Chimes are **Early Access** and cannot be published until dynamic scopes reach GA; sensor events are not queryable through Event History and are not stored for partners, so a missed sensor webhook is unrecoverable ([Configure](https://developer.amazon.com/docs/ring/configure.html); [API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). Ring's new default **TAKE encryption** (rolling out from September 2026) and opt-in **E2EE** compound this: during the initial rollout a TAKE device stays visible but returns unreadable video, and E2EE devices are not returned by the API at all, so video tools must check `e2e_encryption.enabled` and degrade gracefully ([Developer FAQ Q9–Q13](https://developer.amazon.com/docs/ring/developer-faq.html); [Release Notes Sep 16 & Oct 9, 2026](https://developer.amazon.com/docs/ring/release-notes.html)). There is **no official Ring Partner SDK** ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)).

Two distribution tracks exist. A **public app** requires a verified developer account (mandatory government-ID verification of the account owner), a privacy-and-legal certification (90% of submissions reviewed in under 48 hours), US-only distribution, and a 10% Ring revenue share on paid subscriptions ([Get Started](https://developer.amazon.com/docs/ring/get-started.html); [Certify](https://developer.amazon.com/docs/ring/certify.html); [Program Requirements §5.2, §6](https://developer.amazon.com/docs/ring/program-requirements.html)). A **Private App** track — explicitly for "personal integrations and home automation projects" — skips certification and Appstore listing, follows a Configure → Build → Connect lifecycle, and each connected account needs an active Ring subscription or ~30-day trial ([Developer FAQ Q15–Q18](https://developer.amazon.com/docs/ring/developer-faq.html); [Publish](https://developer.amazon.com/docs/ring/publish.html)). The Private App track is the contractually clean path for a hobbyist or family MCP bridge, but it still demands partner-hosted public HTTPS endpoints (Account Link and Token Exchange URLs are required even for private apps) ([Configure](https://developer.amazon.com/docs/ring/configure.html); [Publish](https://developer.amazon.com/docs/ring/publish.html)). Ring's own **"Ring Appstore MCP Server"** is documentation-only — it exposes `search_docs` and `get_doc` against a Bedrock knowledge base and grants **no device access**, despite marketing copy implying otherwise ([Ring MCP](https://developer.amazon.com/docs/ring/ring-mcp.html)).

## The unofficial community API is the only path to alarm and device control

Everything the official API cannot do, the reverse-engineered libraries can. Both `ring-client-api` (TypeScript, MIT, v14.3.0, the richest surface) and `python-ring-doorbell` (LGPL-3.0, v0.9.14, used by Home Assistant) authenticate with the legacy Android "password grant" against `https://oauth.ring.com/oauth/token` using `client_id=ring_official_android`, handle 2FA via HTTP 412, register a device/session at `api.ring.com/clients_api/session` keyed by a stable `hardware_id`, and hold a persistent FCM connection to `mtalk.google.com:5228` for real-time ding/motion/intercom/alarm pushes ([rest-client.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L321-L340); [auth.py](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L65-L118); [api.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/api.ts#L241-L249)). Refresh tokens rotate and must be persisted on every `onRefreshTokenUpdated` callback; reusing a stale token breaks push notifications permanently, and only one live process may use a given token ([dgreif wiki: Refresh-Tokens](https://github.com/dgreif/ring/wiki/Refresh-Tokens)).

**Ring Alarm control** runs over a per-location websocket: the client fetches a ticket from `clap/tickets?locationID=…&requestedTransport=ws`, connects to `wss://{host}/ws?authcode={ticket}`, and sends `security-panel.switch-mode` with `mode` = `none`/`some`/`all` (disarmed/home/away) plus an optional `bypass` array of sensor zids ([location.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L360-L376)). Critically, **no PIN or code is sent or checked at the API level** — Ring's own app documents that "Your PIN is not required when you use the app to change modes" ([Ring support: Arming and disarming](https://ring.com/support/articles/8fscc/Arming-and-disarming-Ring-Alarm)). The siren uses `security-panel.sound-siren`/`silence-siren`, and "panic" is a separate REST call to `rs/monitoring/accounts/{loc}/assets/{uuid}/userAlarm` that dispatches professional-monitoring response and should be used with extreme care ([location.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L495-L528); [ring-mqtt FAQ](https://github.com/tsightler/ring-mqtt/wiki/Frequently-Asked-Questions-(FAQ))). Alarm state is derived from the panel's `mode`, `transitionDelayEndTimestamp` (exit delay) and `alarmInfo.state` (entry-delay/triggered type) ([ring-types.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-types.ts#L214-L240)). Commands are **fire-and-forget with no ack**, and `setAlarmMode` waits indefinitely for the next panel update, so a bridge must add its own timeout and confirm by reading `mode` back — ring-mqtt does exactly this, retrying up to 5 times ([ring-device.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-device.ts#L81-L106); [security-panel.js](https://github.com/tsightler/ring-mqtt/blob/0a34496f4d583e663e1fa7136f6d4602c208e57f/devices/security-panel.js#L265-L331)).

Beyond alarm, the unofficial path covers cameras (floodlight/siren on-off, motion detection, snapshots), chimes (play sound, snooze, volume, nightlight), intercom unlock (JSON-RPC to `commands/v1/devices/{id}/device_rpc`), 1st-gen smart lighting (Beams bridge on the same websocket), Z-Wave locks/switches/dimmers/fans/thermostats/valves paired to the base station, and location Modes for non-alarm sites ([ring-camera.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-camera.ts#L333-L407); [ring-chime.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-chime.ts#L88-L168); [lib/ring.js](https://github.com/tsightler/ring-mqtt/blob/0a34496f4d583e663e1fa7136f6d4602c208e57f/lib/ring.js#L312-L410)). Live video uses Ring's WebRTC service (SIP was removed in 2022) with a ~10-minute session cap, and ring-mqtt converts it to RTSP via a Go gateway `ringstream` in its unreleased v6 ([ring-mqtt wiki: Video Streaming](https://github.com/tsightler/ring-mqtt/wiki/Video-Streaming); [webrtc-connection.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/streaming/webrtc-connection.ts#L49)). The dominant failure modes are well documented: Cloudflare-WAF `406` blocks on datacenter/VPN IPs and bot-like header sets (the 2026 wave is fixed by sending the full versioned app User-Agent), "Authorized Client Device" drift when a new device registers on every restart, FCM socket fragility behind ad-blocking DNS, 12-hour session recreation for non-US data-residency, and roughly one breaking Ring/Google-side change per year (FCM v1 in 2024, websocket in 2025, push decryption in 2026) ([dgreif/ring #1717](https://github.com/dgreif/ring/issues/1717); [dgreif wiki: Notification-Troubleshooting](https://github.com/dgreif/ring/wiki/Notification-Troubleshooting); [ring-mqtt CHANGELOG v5.9.3](https://github.com/tsightler/ring-mqtt/blob/0a34496f4d583e663e1fa7136f6d4602c208e57f/docs/CHANGELOG.md)). There is **no local API**: if Ring's cloud is down, no community integration can read or control anything ([ring-mqtt FAQ](https://github.com/tsightler/ring-mqtt/wiki/Frequently-Asked-Questions-(FAQ))).

Library choice matters. `ring-client-api` (MIT, ESM-only since v14, Node ≥20) has the fullest surface and most engaged maintainers, but the auth and v3-API fixes sit in unmerged PRs and ring-mqtt has forked and then abandoned it for its own embedded v3 client ([CHANGELOG](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/CHANGELOG.md); [ring-mqtt dev CHANGELOG](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/docs/CHANGELOG.md)). `python-ring-doorbell` (LGPL-3.0) is stable but slowing, has **no location-mode or alarm control** at all, and lags on new device kinds ([const.py](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/const.py); [PyPI history](https://pypi.org/project/ring-doorbell/#history)). Shared/secondary Ring accounts are a known blind spot in both released libraries in 2026; only Ring's `device_info/v3` and `evm/v3` endpoints (vendored in tsightler's branch) return their devices ([PR #1749](https://github.com/dgreif/ring/pull/1749)).

## The existing bridge landscape leaves a clear gap for a Ring-semantic MCP

The most feature-complete open bridge is **ring-mqtt** (MIT, ~800 stars): full alarm arm/disarm/bypass/panic/siren, Z-Wave peripherals, cameras with RTSP live and recorded-event playback, chimes, intercom, 1st-gen lighting, and location modes, all published to MQTT with Home Assistant discovery ([ring-mqtt wiki](https://github.com/tsightler/ring-mqtt/wiki)). It is Linux/Docker-only. **Home Assistant core's `ring` integration** is actively maintained and covers doorbells, cameras (WebRTC live view plus last-recording), chimes and intercoms, but **has no Ring Alarm support** — there is no `alarm_control_panel` platform, and HA users get Alarm only by adding ring-mqtt ([HA Ring docs](https://www.home-assistant.io/integrations/ring/); [HA issue #177181](https://github.com/home-assistant/core/issues/177181)). **homebridge-ring** (the `ring-client-api` reference consumer) bridges alarm, cameras with two-way audio, and lighting to HomeKit; **Scrypted's** Ring plugin does HomeKit/HKSV but has been stale since mid-2025; **go2rtc** added a native MIT-licensed Ring video source (RTSP/WebRTC with two-way audio and snapshots) in v1.9.13 ([homebridge-ring README](https://github.com/dgreif/ring/tree/main/packages/homebridge-ring); [Scrypted Ring plugin](https://github.com/koush/scrypted/tree/main/plugins/ring); [go2rtc internal/ring](https://github.com/AlexxIT/go2rtc/blob/master/internal/ring/README.md)).

Existing **Ring MCP servers are immature**. The official MCP registry has zero Amazon-Ring servers. Unofficial-API servers are `jpcors/ring-mcp` (ring-client-api 11.x, stale since 2025-07, likely broken on current Ring backends — an inference, untested), `sandraschi/ring-mcp` (Python, WIP, claims tools beyond library support), and `@striderlabs/mcp-ring` (browser automation, most fragile and ToS-exposed) ([jpcors/ring-mcp](https://github.com/jpcors/ring-mcp); [sandraschi/ring-mcp](https://github.com/sandraschi/ring-mcp); [markswendsen-code/mcp-ring](https://github.com/markswendsen-code/mcp-ring)). Partner-API servers `ring-partner-mcp` (read-only) and `ring-vision-mcp` (WHEP signaling) are 0-star and created Sept–Oct 2026, alongside several Amazon-hackathon use-case apps ([ring-partner-mcp](https://github.com/inslot2525-ctrl/ring-partner-mcp); [ring-vision-mcp](https://github.com/SwaggyXO/ring-vision-mcp)). The strongest indirect path is **Ring → Home Assistant → MCP** via HA core's `mcp_server` or the popular `ha-mcp` (5.2k stars, has a camera-image tool), but HA core's MCP **does not support Notifications**, so it cannot push doorbell events to the model, and it inherits HA's missing Alarm unless ring-mqtt is added ([HA MCP Server](https://www.home-assistant.io/integrations/mcp_server/); [ha-mcp](https://github.com/homeassistant-ai/ha-mcp)). The gap in the market is a well-maintained, Ring-semantic MCP offering durable event cursors, inline snapshots plus resource links, gated alarm control, and a choice of backend — which nobody does today.

## MCP's event and media limits force a layered ingestion design

The current MCP revision **2026-07-28** is a breaking, **stateless** redesign: no `initialize` handshake, no `Mcp-Session-Id`, server-to-client requests replaced by Multi Round-Trip Requests (MRTR), and `subscriptions/listen` replacing `resources/subscribe` ([MCP Versioning](https://modelcontextprotocol.io/specification/versioning); [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Crucially, **core MCP has no primitive that wakes the agent on an external event**. It has only change notifications (list-changed, resource-updated) that tell a client something changed, not that the model should act, and 2026-07-28 even **removed SSE stream resumability**, so a dropped stream loses the in-flight request ([Resources 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources); [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Real "push a doorbell ding to the agent" exists only through three non-portable, immature mechanisms: the **draft Events extension SEP-3415** (opened Oct 5, 2026, unmerged), **ChatGPT's MCP Events** (webhook-only, **requires 2026-07-28**), and **Claude Code "channels"** (stdio, research preview, which **fail under 2026-07-28 and need legacy negotiation**) ([PR #3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415); [OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events); [Claude Code channels](https://code.claude.com/docs/en/channels-reference)). Because client support is split this way, a bridge serving "any MCP client" must be **dual-era** (answering both 2026-07-28 and the legacy 2025-11-25 handshake), and the only portable event baseline is a **durable server-side event log plus a cursor-based `get_events(since_cursor, types, device_ids, limit)` tool** that returns `structuredContent` and an opaque `next_cursor`, with resource-updated notifications used only as cache-invalidation hints ([Versioning and Compatibility 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).

For media, MCP natively supports base64 `image` and `audio` content blocks, embedded resources, and `resource_link`s, but has **no video content type and no streaming primitive** ([Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). Practical client caps bite hard — Claude Code warns above 10,000 tokens and truncates at 25,000, and base64 screenshots have blown past that — so snapshots should be returned as a **downscaled JPEG image block plus a full-resolution `resource_link`**, clips as a `resource_link` plus sampled frames (`get_clip_frames`), and live view only through an MCP App embedded player or a short-lived human-facing stream handle ([Claude Code: MCP](https://code.claude.com/docs/en/mcp); [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)). For safety-critical control, the spec offers only **hints** (tool annotations clients may ignore and must treat as untrusted) and SHOULD-level human-in-the-loop guidance, so a bridge controlling alarms and locks must enforce everything server-side: a two-step `propose_<action>` → `confirm_<action>(confirmation_id)` pattern with **server-minted, user-bound, expiring confirmation IDs** (possession of a handle must never count as authentication), fail-closed on decline, idempotency keyed by request ID, rate limits, and an append-only audit log ([Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Security Best Practices 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)). Camera frames, device names and event text are **untrusted input** — OCR-able text held up to a doorbell is a demonstrated visual prompt-injection vector (up to ~64% black-box success in one note's cited study) — so a bridge must never let event payloads or image content directly trigger control, and Ring credentials must enter only via URL-mode elicitation or local CLI setup, never through form elicitation or tool arguments ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-image-prompt-injection-multimodal-llm-2026/); [Elicitation 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). On SDK choice, **TypeScript** is the natural fit — `ring-client-api` is TypeScript, Claude Code channels are documented against `@modelcontextprotocol/sdk`, and MCP Apps tooling is TS-first — with Python (on `python-ring-doorbell`) a credible Tier-1 alternative; both are Tier 1 as of July 2026 ([MCP blog 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [SDK Tiering](https://modelcontextprotocol.io/community/sdk-tiers)).

## Legal, privacy, and safety constraints shape what the bridge may do

Ring's consumer ToS (effective 2025-11-06) has no explicit anti-bot/scraping clause, but §2(h) bans reverse-engineering and "bypass[ing] any security" of the Software, and §2(a) lets Ring terminate accounts at its discretion — language a third-party tracker rates "High severity" and ties to the US CFAA ([Ring Terms](https://ring.com/terms); [ConductAtlas](https://conductatlas.com/platform/ring/ring-terms-of-service/prohibition-on-reverse-engineering-software/)). The notes found **no cease-and-desist, DMCA takedown, lawsuit, or public statement** against dgreif/ring, ring-mqtt, python-ring-doorbell or Home Assistant; enforcement has been passive and technical (WAF bot-scoring, IP blocks, endpoint and push changes, encryption), and all projects remain active ([dgreif/ring #1717](https://github.com/dgreif/ring/issues/1717)). The official program's Program Requirements are far more specific: partners may access the service only "through the authentication methods we specify" and must not circumvent security (§2.5), must not use the service where failure "could lead to death" (§2.8), must not trigger or interface with alarm services without governmental licenses (§2.19), must not share developer credentials (§2.7(iii)), and must not use a product name "confusingly similar to 'Ring' [or] 'Amazon'" (§3) — which directly implicates the working name **"RingMCPBridge"** for any published app ([Program Requirements](https://developer.amazon.com/docs/ring/program-requirements.html)). The Content Policy bans identifying untagged individuals, cross-property movement profiles, and standing law-enforcement access ([Content Policy](https://developer.amazon.com/docs/ring/content-policy.html)). Ring's history — 2019 credential-stuffing takeovers, the 2023 **FTC $5.8M order** (insider video access, 20-year security program, deletion of models derived from improperly reviewed video), Familiar Faces facial recognition and its June 2026 class action, and the Search Party/Flock backlash — means regulators and the public treat Ring video, credentials, and biometric-derived outputs as high-sensitivity data ([FTC press release](https://www.ftc.gov/news-events/news/press-releases/2023/05/ftc-says-ring-employees-illegally-surveilled-customers-failed-stop-hackers-taking-control-users); [EFF](https://www.eff.org/deeplinks/2025/11/legal-case-against-rings-face-recognition-feature)). Sending frames to a cloud LLM makes the bridge a third-party processor that must disclose the sharing, reach downstream deletion, and avoid training on footage; the GDPR household exemption is lost once a doorbell captures public space (*Ryneš*), and face matching triggers BIPA/Texas CUBI/Washington/Israel Amendment-13 regimes ([Content Policy §4.1.2–4.1.3](https://developer.amazon.com/docs/ring/content-policy.html); [EDPB Guidelines 3/2019](https://www.edpb.europa.eu/sites/default/files/files/file1/edpb_guidelines_201903_video_devices_en.pdf)).

Because Ring enforces **no step-up authentication** for arming, disarming, unlocking, or panic at the API level — whoever holds a refresh token can do all of it — and because existing integrations add their own guardrails (ring-mqtt's UI-only disarm code, panic off by default, homebridge's `allowDisarm`, HA core omitting alarm entirely), the bridge must impose its own risk tiers and confirmation. Ring's own Alexa integration requires a spoken PIN to disarm or unlock, setting a clear precedent ([location.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L360-L376); [Ring support: Arming and disarming](https://ring.com/support/articles/8fscc/Arming-and-disarming-Ring-Alarm); [Ring support: Smart Locks + Alexa](https://ring.com/support/articles/od8uw/Controlling-Works-with-Ring-Smart-Locks-with-Alexa)).

| Tier | Example actions | Required safeguard |
|---|---|---|
| Read-only | All state resources, event history, device listing | None (annotate `readOnlyHint: true`) |
| Low | Lights on/off and brightness; chime play/snooze; volumes | Rate limit |
| Medium | Camera motion-detection/warning off; location mode change; camera siren; **arm** (home/away) | Confirmation; audit log |
| High | **Disarm**; sensor bypass; **lock/intercom unlock**; valve close; thermostat change | Server-side PIN + out-of-band human confirmation; never in model context; fail closed |
| Critical (off by default) | **Panic burglar/fire** (dispatches authorities); intercom invite/remove access | Explicit opt-in; separate action (never map "panic off" to disarm); full audit |

## Design implications and open decisions for the product design workshop

The evidence points to a **hybrid bridge with a core Ring adapter and per-backend capability flags**, not a single-path design. The stated scope — doorbells, cameras, **Ring Alarm sensors/status**, events, media, and **control where possible** — cannot be met by the official API alone, because the official Partner API has no alarm mode read, no arm/disarm, no keypad, and treats sensors as Early Access telemetry rather than alarm-panel state. Alarm and device control require the unofficial path (directly via `ring-client-api`, or composed over ring-mqtt's MQTT/RTSP). A clean architecture is a **core adapter** (auth, device model, event ingestion, policy, audit) with swappable backends — official for sanctioned reads/events/video where readable, unofficial for alarm/control — exposing a modest set of **intent-level MCP tools** (`list_devices`, `get_device_state`, `get_alarm_state`, `get_events`, `get_snapshot`, `get_event_clip`, and gated `arm_home`/`arm_away`/`disarm`/`unlock`) over **thin, dual-era MCP front-ends**: a remote Streamable HTTP server with CIMD OAuth for ChatGPT/claude.ai/IDEs, and a local stdio server or Claude Code channel for desktop. Event ingestion rests on a **durable server-side event log plus a cursor `get_events` tool** as the portable baseline, with ChatGPT SEP-3415 webhooks and Claude Code channels as host-specific "wake the agent" adapters, and resource-updated notifications treated only as cache hints. Media handling means downscaled inline snapshots plus resource links, clips as links plus sampled frames, and short-lived explicitly-torn-down live sessions (live view suppresses the very motion events the bridge exists to report, and video is increasingly blocked by TAKE/E2EE). The safety model enforces confirmation, server-side PINs never placed in model context, fail-closed confirmation IDs, idempotency, panic off by default, and an audit trail — because Ring enforces none of this itself. Deployment should be **home/residential single-user first**: both backends dislike datacenter IPs (unofficial gets WAF 406; official needs allowlisted static egress), the refresh token grants full account access and should sit in an OS keychain, and multi-user hosting turns the operator into a high-value target and a privacy-law processor. TypeScript is the leading language choice given `ring-client-api` and the MCP tooling ecosystem.
