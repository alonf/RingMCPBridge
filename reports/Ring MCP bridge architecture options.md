# Run Ring at home, serve MCP from Azure

Build the bridge in two halves. A **.NET 10 ASP.NET Core MCP server in Azure** (Container Apps pinned to one replica, or App Service B1 with Always On, roughly $13–15 a month) is the public, OAuth-protected, dual-era Streamable HTTP endpoint for every MCP client, and it holds the event log, the confirmation policy and the push adapters; a **small Ring connector at home on the residential IP** alone holds the Ring identity, the Alarm websocket, FCM push and camera media, and connects to Azure outbound only. A local stdio process is still required for exactly one thing, **unsolicited push into a running Claude Code session**, because Claude Code "channels" still need a stdio subprocess on the legacy handshake; claude.ai, Claude Desktop, Claude mobile, ChatGPT and Foundry agents are all served remotely, and only ChatGPT has true remote push, through webhook MCP Events. .NET 10 is first-class for the MCP side but poor for the Ring side: no maintained C# Ring library exists, FCM push receiving has no .NET implementation, and SIPSorcery, the only mature managed WebRTC stack, forbids use inside Israel by license, so the Ring connector should be polyglot (a Node sidecar on a patched `ring-client-api`, werift or Go/pion media, and ffmpeg) behind a Ring-agnostic contract. Microsoft Foundry is an optional MCP *client* of the bridge, never its host. Ring's blocking of datacenter and VPN IPs is documented against other providers rather than Azure, but it is reputation-driven and probabilistic, so the unofficial path belongs at home whatever a one-off Azure probe shows. The official Ring Partner API admits "Ring accounts from any country" through a private app, yet it has an unresolved US-only device rule and no Ring Alarm surface, and hosting in Azure US changes no eligibility gate beyond requiring an allowlisted static egress IP. For vision, the agent's default is one fresh, downscaled JPEG chosen by each camera's power mode, with live views as gated, rate-limited actions and an MCP Apps viewer for humans.

## Only Claude Code push still needs a local stdio process

The MCP half of a .NET design rests on solid ground. The official C# SDK went GA at v1.0.0 in February 2026. **v2.0.0 shipped on 2026-07-28**, "in stable alignment with the MCP 2026-07-28 specification", while keeping "down-level interoperability for peers negotiating 2025-11-25 and earlier". **v2.3.0 (2026-10-20)** ships dedicated net10.0 assets ([v2.0.0 release](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.0.0); [NuGet ModelContextProtocol.AspNetCore](https://www.nuget.org/packages/ModelContextProtocol.AspNetCore)).

One endpoint can serve both protocol eras. The **`StatefulForInitializeClients`** session mode, added in v2.2.0, gives legacy `initialize` clients full sessions with server-to-client requests, and serves 2026-07-28 clients statelessly per request ([v2.2.0 release](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.2.0); [stateless.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/stateless/stateless.md)). Since v2.1.0 a custom `subscriptions/listen` handler can stream notifications over the held-open POST even under stateless HTTP ([PR #1775](https://github.com/modelcontextprotocol/csharp-sdk/pull/1775)).

The gaps matter just as much. The SDK includes **no OAuth authorization server**: it is a resource server and a client only. It has **no MCP Events support** and **no WebSocket transport** ([transports.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/transports/transports.md); [csharp-sdk tests tree](https://github.com/modelcontextprotocol/csharp-sdk/tree/main/tests)). In v2.3.0, modern responses also withhold headers until the first protocol message. A long-running silent handler therefore needs progress output or a generous HTTP timeout ([v2.3.0 release](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.3.0)).

| Client | Consumes the Azure endpoint? | Real-time push path | Local stdio needed? |
|---|---|---|---|
| Claude Code CLI | Yes. HTTP with OAuth (CIMD, DCR or a pre-registered client); 2026-07-28 by default | Channels (stdio, legacy handshake, research preview), or MCP Tasks "wait" (remote, beta, v2.1.304+) | **Only for channels** |
| Claude Code in VS Code or the desktop app | Yes | No MCP Tasks; channels unverified | No, for tools |
| claude.ai, Claude Desktop, Claude mobile | Yes, as a remote connector reached from Anthropic's cloud | None documented | **No.** A local process cannot add push |
| ChatGPT (Work chats) | Yes. Public HTTPS, OAuth 2.1 with S256 | MCP Events webhooks (2026-07-28 only) | No |
| Microsoft Foundry agents | Yes. Remote endpoints only | None; the bridge must invoke the agent | No. Foundry cannot use one |

The stdio requirement comes from Claude Code's channel contract alone. "A channel is an MCP server that runs on the same machine as Claude Code. Claude Code spawns it as a subprocess and communicates over stdio" ([Claude Code: Channels reference](https://code.claude.com/docs/en/channels-reference)). On the v2 runtime, "a channel server that negotiates MCP protocol revision 2026-07-28 can't deliver channel messages", while one that doesn't support that revision "connects on the earlier handshake and registers as before" ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)).

Channels are still a **research preview**. Custom channels need a `--dangerously-load-development-channels` flag, and Team and Enterprise organizations must explicitly enable them. Pro and Max users without an organization skip those checks. Channels are unavailable on Bedrock, Google's Agent Platform and Microsoft Foundry ([Claude Code: Channels](https://code.claude.com/docs/en/channels)).

The trap is negotiation. Since v2.1.292 (2026-10-06), Claude Code negotiates 2026-07-28 with stdio servers by default ([Claude Code CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The documented opt-out, `MCP_PROTOCOL_NEGOTIATION=legacy`, "keeps every server on it". That would also drag the Azure bridge onto the legacy handshake in that session and **rule out MCP Tasks** ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)).

The cleaner route is to pin the shim itself. Setting a C# server's `ProtocolVersion` to `2025-11-25` makes it "reject `2026-07-28` per-request metadata" ([McpServerOptions.cs](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/src/ModelContextProtocol.Core/Server/McpServerOptions.cs)). That should register the shim as a legacy channel while the Azure bridge stays on 2026-07-28. This is undocumented, because the channel docs name only the TypeScript SDK, so test it first and keep a TypeScript shim as the documented fallback. The shim holds no Ring state. It subscribes outbound to Azure and re-emits events as `notifications/claude/channel`. Events "only arrive while the session is open" ([Claude Code: Channels](https://code.claude.com/docs/en/channels)).

Claude Code also offers a remote-only alternative that needs no shim. **MCP Tasks** are in public beta from v2.1.304, and "If Claude is idle when the result arrives, Claude starts on it unprompted" ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)). A `ring_wait_for_event` tool answered as a task, through `ModelContextProtocol.Extensions.Tasks`, becomes a wake-up call. The SDK's task store is shared across stateless instances ([stateless.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/stateless/stateless.md)). The limits are real. The agent starts each wait and must re-arm it. Tasks work only in the CLI, in sessions that fetch feature flags, and only in the main conversation.

**ChatGPT is the only client with true remote push.** MCP Events "requires MCP 2.0 (protocol version `2026-07-28`)". It is webhook-only, signed in the Standard Webhooks HMAC format and capped at 256 KiB per delivery, and polling and streaming are not supported ([OpenAI: MCP Events](https://developers.openai.com/plugins/build/mcp-events)).

In C# the Events surface must be hand-rolled: `events/*` methods through the experimental `RequestHandlers` hook, durable subscription storage, and a signed webhook sender ([McpServerRequestHandler.cs](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/src/ModelContextProtocol.Core/Server/McpServerRequestHandler.cs)). One real obstacle is unverified. OpenAI expects a **top-level `capabilities.events`** key in `server/discover`, and the SDK's typed `ServerCapabilities` has no catch-all for one ([ServerCapabilities.cs](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/src/ModelContextProtocol.Core/Protocol/ServerCapabilities.cs)). Patching the discover result with an outgoing message filter is the likely workaround. Prototype it in week one. SEP-3415, the vendor-neutral Events extension, is still an open draft PR, so keep Events behind an adapter ([PR #3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)).

The Claude apps have no push path to target at all. claude.ai, Desktop and mobile share one connector infrastructure. It doesn't support "Resource subscriptions; Sampling; Advanced or draft capabilities", and it caps tool results at about 150,000 characters and 240 seconds ([Build an MCP server for Claude](https://claude.com/docs/connectors/building)). Connections originate from Anthropic's cloud (`160.79.104.0/21`), so a server that is only local cannot be a connector ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication)). For these clients, "push" means a cursor-based `get_events(since)` tool plus an MCP App dashboard.

A stdio process also cannot *be* the bridge. It lives and dies with one client session, while Ring ingestion needs sockets open 24/7 and refresh-token persistence that survives restarts ([dgreif wiki: Refresh-Tokens](https://github.com/dgreif/ring/wiki/Refresh-Tokens)).

Two further requirements follow. First, one external authorization server must satisfy every client. Claude supports DCR and CIMD by default, and uses CIMD only when the authorization server advertises both `client_id_metadata_document_supported: true` and `none` client authentication. It also needs form-urlencoded token requests and a 401 to start sign-in ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication)). ChatGPT prefers CIMD and requires S256 PKCE and RFC 9207 `iss` validation ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)). Microsoft Entra, if used, lacks Dynamic Client Registration, and it needs a custom domain before the MCP URL can serve as an Application ID URI (error `AADSTS9010010`) ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication); [csharp-sdk issue #1446](https://github.com/modelcontextprotocol/csharp-sdk/issues/1446)). Second, the host must tolerate long-held responses. If streams are cut repeatedly, after five reopens in an hour Claude Code waits about six hours before the next ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)). Azure's front-end timeouts for held-open POSTs remain unverified.

## C# owns the MCP core, but Ring's edge belongs to Node and Go

No C# Ring library can be taken as a dependency. **KoenZomers.Ring.Api**, the only real NuGet package, last released 1.0.0 on 2024-10-23. It is REST-only, with no Alarm websocket, push, modes or device control. It is licensed **EPL-2.0** on NuGet despite an MIT badge in the README. And it is broken by 2026's `406` auth responses, in an issue open since March with no maintainer reply ([NuGet KoenZomers.Ring.Api](https://www.nuget.org/packages/KoenZomers.Ring.Api/1.0.0); [Api.csproj L20](https://github.com/KoenZomers/RingApi/blob/452e1b788b7785f62d53713ff2094b65f43a2da8/Api/Api.csproj#L20); [KoenZomers/RingApi #37](https://github.com/KoenZomers/RingApi/issues/37)).

The broadest C# Ring code is embedded in **rsperry79/VideoForensics**. It targets net10.0 under MIT and covers the Alarm websocket, modes, lights and live-view signalling. But it is a two-month-old application with 0 stars, its own comments call parts of it "best-effort", and it has **no FCM receiver**. Its code notes that Ring rejects push subscriptions with HTTP 422 "Client Device required" from a headless client. Its provenance is also unclear: it credits a GitHub repo that returns 404 and ships KoenZomers' strong-name key ([VideoForensics](https://github.com/rsperry79/VideoForensics); [Session.EventSubscriptions.cs](https://github.com/rsperry79/VideoForensics/blob/7508a00cac4556a305e853558c36fa59481f9dea/src/providers/ring/core/src/Session.EventSubscriptions.cs#L6-L17); [CREDITS.md](https://github.com/rsperry79/VideoForensics/blob/7508a00cac4556a305e853558c36fa59481f9dea/CREDITS.md#L29-L33)). It is a useful reference, not a dependable upstream.

A port is therefore the only all-C# route, and its size is knowable. Excluding streaming, `ring-client-api` is about **4.6k lines of TypeScript**, 1,271 of them type definitions ([ring-client-api tree](https://github.com/dgreif/ring/tree/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api)). Its push dependency, `@eneris/push-receiver`, adds about **1.7k hand-written lines plus 0.6k of protobuf definitions**. That code does GCM checkin and register3, Firebase Installations, web-push FCM registration with ECDH keys, the MCS socket, and draft-03 `aesgcm` decryption ([push-receiver src](https://github.com/Eneris/push-receiver/tree/590d6d95f92193f7a320ba556208b3f948f52ddc/src)).

The websocket half is easy. Ring dropped socket.io in `ring-client-api` 14.0.0, so .NET's `ClientWebSocket` suffices ([ring-client-api CHANGELOG](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/CHANGELOG.md)). Push is the hard half, and no NuGet package receives FCM messages. The closest C# pieces don't add up to a working receiver. **RustPlusApi.Fcm** (MIT, net10.0, active in October 2026) has the MCS socket, checkin, register3 and Firebase Installations, but no web-push registration and no ECE decryption ([HandyS11/RustPlusApi](https://github.com/HandyS11/RustPlusApi)). **ekalchev/push-notificator-csharp** has a BouncyCastle decryptor, but it was last touched in 2022 and uses a legacy subscribe endpoint ([ekalchev/push-notificator-csharp](https://github.com/ekalchev/push-notificator-csharp)). Python, by contrast, has a maintained receiver in `firebase-messaging` ([sdb9696/firebase-messaging](https://github.com/sdb9696/firebase-messaging)).

A sizing estimate derived from these counts, not a measured figure, puts a C# port to parity at roughly **6–9k lines and 5–9 person-weeks**, with the FCM receiver the riskiest 2–4 weeks. The same estimate puts a Node sidecar over the existing library at roughly **300–800 lines and 1–2 weeks**.

Maintenance tips the decision. Ring and Google have broken third-party clients at least once a year. In July 2023 the client ID had to switch from Windows to Android "to restore the service" ([KoenZomers README](https://github.com/KoenZomers/RingApi/blob/452e1b788b7785f62d53713ff2094b65f43a2da8/README.md)). In September 2024 `client_id` became required on the initial token request, breaking every earlier python-ring-doorbell release ([python-ring-doorbell PR #446](https://github.com/python-ring-doorbell/python-ring-doorbell/pull/446)). In May 2025 the Alarm websocket changed ([ring-mqtt v5.8.1](https://github.com/tsightler/ring-mqtt/releases/tag/v5.8.1)). Early 2026 brought two breaks: the FCM `crypto-key` header format changed ([dgreif/ring #1709](https://github.com/dgreif/ring/issues/1709)), and Cloudflare-WAF 406s accompanied the move to `/oauth/v2` PKCE ([dgreif/ring #1717](https://github.com/dgreif/ring/issues/1717)). Later in 2026, v3 discovery endpoints became required for shared accounts and newer devices ([PR #1749](https://github.com/dgreif/ring/pull/1749)).

Every fix appeared first in the JavaScript or Python communities. Issue #1709 shows both the strength and the trap of riding that ecosystem. The decryption fix shipped in `push-receiver` 4.3.1 on 2026-02-27. Yet the latest published `ring-client-api`, 14.3.0 from 2026-02-08, still pins 4.3.0, and users were still hitting the bug in October ([npm @eneris/push-receiver](https://registry.npmjs.org/@eneris/push-receiver); [npm ring-client-api](https://registry.npmjs.org/ring-client-api); [dgreif/ring #1709](https://github.com/dgreif/ring/issues/1709)).

Use Node for the Ring edge, but not the published package as-is. There are three workable bases. The first forces `push-receiver` 4.4.0 over upstream 14.3.0 with npm `overrides`. The second is **`@tsightler/ring-client-api` 15.0.0-beta.2**, which carries PKCE and the v3 endpoints. The third vendors ring-mqtt v6's embedded `lib/ring-client/`, 3,251 MIT lines on an untagged branch ([npm @tsightler/ring-client-api](https://registry.npmjs.org/@tsightler%2fring-client-api); [ring-mqtt lib/ring-client](https://github.com/tsightler/ring-mqtt/tree/996be5b73537d845f9176eef6efcf5ed055be85e/lib/ring-client)). All three inherit the same bus factor: one maintainer, tsightler, produced most of 2026's fixes.

The sidecar is a Node 24 process that owns Ring auth state. It persists the wrapped refresh token and the push credentials atomically on every rotation, and exposes a narrow localhost API: request/response calls for devices, alarm, snapshots and history, plus an SSE or WebSocket stream of normalized events. The .NET side treats it as an anti-corruption layer. Two runtimes in one deployment have direct precedent. ring-mqtt v6 builds a Go stage into a `node:krypton-alpine` image supervised by s6-overlay ([ring-mqtt Dockerfile](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/Dockerfile)). Azure Container Apps sidecars "share hard disk and network resources and experience the same application lifecycle" ([Learn: Containers in ACA](https://learn.microsoft.com/en-us/azure/container-apps/containers)). The cost is a second dependency tree, a versioned internal contract, and two toolchains.

One rule binds every variant: **exactly one process holds the Ring token and hardware ID, and everything else asks it for work.** The rule rests on two Ring behaviors. A token "encode[s] information about the hardware ID", and using it from another system "can lead to the system in question being blocked" ([dgreif/ring #1493](https://github.com/dgreif/ring/issues/1493)). And re-registering push credentials for a device Ring already knows silently kills push ([dgreif/ring #1860](https://github.com/dgreif/ring/issues/1860)).

Media is where .NET fails outright for this user. **SIPSorcery**, the only mature managed WebRTC stack, carries an "Additional Use Restriction": "Use, modification, or distribution inside Israel and the Occupied Territories is not permitted". The license declares that restriction "superior" to its BSD-3-Clause terms ([sipsorcery LICENSE.md](https://github.com/sipsorcery-org/sipsorcery/blob/caa180d767c75668c9856419821df43c58db3f19/LICENSE.md)). That is a factual reading of the text, not legal advice. The engineering lesson is that SIPSorcery's NuGet packages declared `BSD-3-Clause` until a July 2026 commit admitted the metadata "misrepresented the actual terms", so an automated package-license scan would have missed the clause ([SIPSorcery LICENSE.md commit history](https://api.github.com/repos/sipsorcery-org/sipsorcery/commits?path=LICENSE.md)).

The only other managed option, **tryAGI.WebRTC** (MIT, .NET 10), calls itself "Experimental 0.x" and "not … a security-audited general WebRTC stack" ([NuGet tryAGI.WebRTC](https://www.nuget.org/packages/tryAGI.WebRTC)). The media path therefore leaves .NET too. Day one uses `ring-client-api`'s own werift-based streaming feeding ffmpeg, the most proven route ([ring-client-api package.json](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/package.json); [browser-example.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/examples/browser-example.ts)).

Once ring-mqtt v6 is tagged, the follow-on is **ringstream**, an MIT Go/pion gateway. It was designed so that the session owner "stays the only thing that can mint a signaling ticket" ([ringstream control.go](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/ringstream/control.go#L13-L17)). Its control protocol is internal to an untagged release ([ring-mqtt dev commits](https://github.com/tsightler/ring-mqtt/commits/dev)).

**go2rtc** is ruled out as long as it would share a token. Its Ring source runs with a nil refresh callback, so it never persists rotated tokens, and its API listens on `:1984` without authentication by default ([go2rtc client.go L56](https://github.com/AlexxIT/go2rtc/blob/c245815e75e2a5fd60b4290f12bfc04e55a984d3/pkg/ring/client.go#L56); [go2rtc API README](https://github.com/AlexxIT/go2rtc/blob/c245815e75e2a5fd60b4290f12bfc04e55a984d3/internal/api/README.md)). On the .NET side, FFMpegCore (MIT, with pipe input and output) turns streams into JPEGs without native bindings ([FFMpegCore](https://github.com/rosenbjerg/FFMpegCore)).

A pure-C# Ring client is justified only by a hard single-runtime requirement, or by the goal of shipping the first maintained .NET Ring library. Even then the sensible order is strangler-style: REST and websocket first, with VideoForensics as a reference, and push last or never. One risk stays open in every option: whether Cloudflare's WAF scores .NET's TLS and header fingerprint differently from Node's `undici` is untested.

## Azure hosts the front door; the home IP keeps Ring talking

Two Azure services fit an always-on bridge. Container Apps fits with a minimum of one replica; Microsoft says to "set the minimum number of replicas to 1 or higher" if an instance must always run ([Learn: Scaling in ACA](https://learn.microsoft.com/en-us/azure/container-apps/scale-app)). App Service fits on Basic or higher with Always On, the setting continuous background work requires (search snippet) ([Learn: How WebJobs run](https://learn.microsoft.com/en-us/azure/app-service/webjobs-execution)). Either costs about **$13–15 a month** for one small instance. The Container Apps figure is computed from third-party unit prices ([devzero](https://www.devzero.io/blog/azure-container-apps-pricing)). Budget the active rate, because heartbeating sockets break the idle-billing conditions: under 0.01 vCPU and under 1,000 bytes per second ([Learn: Billing in ACA](https://learn.microsoft.com/en-us/azure/container-apps/billing)). B1 Linux is about $13.14, per a community answer (search snippet) ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/12322935)). Neither figure includes the static egress IP the official backend needs. On Container Apps that means workload profiles with a NAT Gateway ([Learn: Scaling in ACA](https://learn.microsoft.com/en-us/azure/container-apps/scale-app)), and that cost was not priced.

Azure Functions fits only as a stateless request front end. Its MCP extension is trigger-driven, and self-hosted SDK servers there must be "Stateless servers" on Flex Consumption (search snippet) ([Learn: MCP bindings for Azure Functions](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-mcp); [Learn: Self-hosted MCP servers](https://learn.microsoft.com/en-my/azUre/azure-functions/self-hosted-mcp-servers)). The bridge's front door is more than that, even with the Ring sockets at home. It holds a persistent inbound link from the home edge, held-open `subscriptions/listen` POSTs and a background webhook sender. It must meet Ring's 5-second webhook acknowledgment and 60-second Token Exchange without risking a cold start. And it needs control of `SessionMode`, `RequestHandlers` and outgoing filters, which the Functions extension has not been shown to offer. API Management "supports MCP server tools, but doesn't support MCP resources or prompts", which is wrong for an event-centric bridge ([Learn: MCP servers in APIM](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)).

Plain ASP.NET Core with `ModelContextProtocol.AspNetCore` 2.3.0 keeps every topology open, because the same code runs in Container Apps, App Service or at home. Three settings matter. First, pin the app to one instance. "Replica quantities are a target amount, not a guarantee", and upgrades pre-warm extra replicas ([Learn: Scaling in ACA](https://learn.microsoft.com/en-us/azure/container-apps/scale-app)). Set `maxReplicas = 1` and add a blob-lease lock. The official backend's refresh token rotates, and "each refresh invalidates the previous refresh token" ([Release Notes](https://developer.amazon.com/docs/ring/release-notes.html)), so two instances racing a refresh would strand one. The in-memory live-session handles and held-open listen streams also assume a single process. Second, know the built-in auth's limits: App Service's built-in MCP authorization is in preview and "doesn't provide granular control to individual MCP tools" ([Learn: Configure MCP server authorization](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)). Third, put the endpoint on a custom domain, which Entra requires anyway.

**Microsoft Foundry (formerly Azure AI Foundry) is not a host for this bridge.** Its own docs say "The Agent Service runtime only accepts a remote MCP server endpoint". Local servers must be self-hosted "on Azure Container Apps or Azure Functions" ([Foundry MCP tool doc](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)). Hosted agents do run C# containers, but "Compute follows the session". The platform deprovisions after an idle timeout of 2 to 240 minutes, with no replica count and no warm pool. Each session gets its own VM-isolated sandbox behind fixed, Entra-authenticated endpoints ([Hosted agents concept](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)). That shape cannot hold a Ring websocket for days, or serve `/.well-known` OAuth metadata for Claude and ChatGPT. Toolboxes proxy existing MCP servers, and Azure API Center registers them as catalog metadata, but neither runs code ([API Center MCP](https://learn.microsoft.com/en-us/azure/api-center/register-discover-mcp-server)).

Foundry is therefore one more client, and it brings four constraints for the bridge's tool surface. Non-streaming tool calls time out at **100 seconds**, which rules out long-poll tools. Schemas with `anyOf`/`allOf` or multi-type parameters are rejected, so check what C# nullable parameters emit. `require_approval` defaults to `always`. And OAuth passthrough requires the user's Entra tenant to match the project's tenant ([Foundry MCP tool doc](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol); [Foundry MCP authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)).

Foundry cannot react to Ring events on its own. Routines trigger only on timers, cron schedules (five-minute minimum), GitHub issues or Teams messages ([Routines concept](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/routines)). The bridge must call the agent itself, using a managed-identity token and the Responses API for a prompt agent or the Invocations endpoint for a hosted agent. Prompt agents carry no hosting charge. Hosted sandboxes bill about $0.0994 per vCPU-hour and $0.0118 per memory-hour in East US ([Azure Retail Prices API](https://prices.azure.com/api/retail/prices?$filter=contains(productName,'Agent')%20and%20armRegionName%20eq%20'eastus')). Israel Central is absent from the 31 hosted-agent regions ([Hosted agents concept](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)).

The evidence on IP blocking is consistent and dated, and it comes mostly from tsightler, the ring-mqtt author and a `ring-client-api` collaborator. In 2024, debugging a DigitalOcean droplet, he wrote that "Ring has large amounts of IP blocks in place from various cloud services and VPNs" ([dgreif/ring #1493](https://github.com/dgreif/ring/issues/1493)). In 2025, on an Ionos VPS, he said Ring "bans connections from most IP blocks on those cheap hosting services", and that the 406s hit "basic device enumeration API endpoints", not just login ([dgreif/ring #1571](https://github.com/dgreif/ring/issues/1571)). Late that year he estimated that "95% of reports about this issue are people using VPNs or VPS servers in the cloud, which Ring blocks" ([dgreif/ring #1676](https://github.com/dgreif/ring/issues/1676)). In 2026 a Mullvad exit node failed the same way ([dgreif/ring #1712](https://github.com/dgreif/ring/issues/1712)).

Ring's own support article admits only to blocking VPN and abusive IPs ([Ring support: VPNs](https://ring.com/au/en/support/articles/c23si/Understanding-the-Ring-App-and-Virtual-Private-Networks-VPN)). Ring's developer docs, however, state the general mechanism for its official API: requests "from a datacenter or cloud-hosting IP address" can draw 406s "even with the correct headers" ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). **No report names Azure, AWS or GCP either way**, so "Azure is blocked" is a strong inference, not a fact. The WAF also weighs headers together with IP reputation ([dgreif/ring #1717](https://github.com/dgreif/ring/issues/1717)). That makes blocking probabilistic, and it is exactly why a passing probe from Azure today does not license an all-Azure unofficial design. It could fail next month, fleet-wide and silently.

For the unofficial path, that settles the topology as hybrid, and three facts close off the cloud workarounds. Token affinity is permanent, so moving the connector later means a fresh login from the new host, never a token transfer. A static Azure NAT IP still sits inside Azure's published ranges, so it gives the connector a stable identity but does nothing for its reputation. Commercial residential proxies are out. They sit close to the Terms' ban on attempts to "bypass any security" ([Ring Terms](https://ring.com/terms)), and they share exit IPs with other accounts, which is itself a temporary-block trigger ([dgreif/ring #1580](https://github.com/dgreif/ring/issues/1580)).

Routing Azure's Ring traffic out through a home Tailscale exit node works in principle ([Tailscale: Exit nodes](https://tailscale.com/kb/1103/exit-nodes)). It still depends on the home link, though, and adds tunnel failure modes without removing that dependency. A home connector that dials out to Azure dominates it. The outbound link can be Azure Relay Hybrid Connections, billed per listener-hour with 5 GB of data included (search snippet), or a persistent WebSocket or SignalR connection to the Azure app ([Learn: Azure Relay FAQ](https://learn.microsoft.com/en-gb/azure/azure-relay/relay-faq)). An all-at-home variant behind Cloudflare Tunnel is cheaper still, but gives up managed hosting, storage and uptime.

| Component | Runs where | Language | Owns |
|---|---|---|---|
| MCP front door | Azure Container Apps (min = max = 1) or App Service B1 with Always On, on a custom domain | C#, .NET 10, `ModelContextProtocol.AspNetCore` 2.3.0 | Dual-era Streamable HTTP; OAuth resource server; tool policy and confirmations; durable event log and cursors; ChatGPT webhooks; MCP Tasks; Foundry invocations; connector-health resource |
| Official Partner API backend (optional) | Same Azure app, with an allowlisted static egress IP | C# | Token Exchange and Account Link endpoints; webhook receiver; RTSPS frame grabs via ffmpeg |
| Home Ring edge | NUC, NAS or Pi on the residential IP | .NET 10 worker plus Node 24 sidecar, later ringstream (Go), plus ffmpeg | The only Ring token and hardware ID; Alarm websocket; FCM push; snapshots; live sessions; SQLite outbox; back-fill on reconnect |
| Claude Code channel shim (optional) | Each Claude Code user's machine | C# pinned to 2025-11-25, or TypeScript | Re-emitting Azure events as `notifications/claude/channel` |

The hybrid's weakness is outages. A home connector goes deaf when the home internet or power fails, which is exactly when an alarm matters. The Alarm base station appears able to reach Ring over cellular backup: its ticket request sets `enableExtendedEmergencyCellUsage=true` ([location.ts L232-L240](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L232-L240)). A cloud connector would hear it; the home connector cannot. The mitigations are a UPS or LTE failover for the router and the edge box, back-fill from Ring's event and alarm history on every reconnect, and an Azure-side connector-health resource, so agents never read silence as "all quiet". Ring's own app stays the primary alarm channel; Ring's partner terms forbid safety-critical reliance anyway ([Program Requirements](https://developer.amazon.com/docs/ring/program-requirements.html)). The connector must also re-create its Ring session every 12 hours, because outside the US "Ring is clearing the session info after ~24 hours, which breaks Push Notifications" ([rest-client.ts L486-L503](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L486-L503)). That applies directly to an Israeli account. The home edge is also the box that must never run twice, because two processes retrying one rotated Ring token is a documented trigger for temporary IP blocks ([dgreif/ring #1580](https://github.com/dgreif/ring/issues/1580)).

Gated control lives in the Azure core, because Ring enforces none. Ring's app documents that "Your PIN is not required when you use the app to change modes" ([Ring support: Arming and disarming](https://ring.com/support/articles/8fscc/Arming-and-disarming-Ring-Alarm)). The `security-panel.switch-mode` command carries no code at all, and it is fire-and-forget ([location.ts L360-L376](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L360-L376)). The bridge must confirm by reading the mode back, as ring-mqtt does with up to five retries ([security-panel.js](https://github.com/tsightler/ring-mqtt/blob/0a34496f4d583e663e1fa7136f6d4602c208e57f/devices/security-panel.js#L265-L331)).

The core therefore owns the confirmation. Each action is a `propose` followed by a `confirm`, using server-minted, user-bound, expiring confirmation IDs, and the PIN or consent step runs outside the model's context. In C#, `ElicitAsync` throws on every stateless 2026-07-28 request, so the bridge raises `InputRequiredException` through MRTR, which works in both protocol eras, or `UrlElicitationRequiredException` to send the user to a bridge-hosted confirmation page ([elicitation.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/elicitation/elicitation.md)). Claude Code serves elicitation only in interactive terminal sessions ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)). No source documents elicitation on claude.ai, Claude Desktop or ChatGPT, so the confirm step must not depend on it. The portable fallback is a bridge-hosted confirmation link, returned in the tool result, where the user enters the PIN. `Destructive`, `Idempotent` and `ReadOnly` annotations act as hints only, so back them with per-tool `[Authorize]` roles ([McpServerToolAttribute.cs](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/src/ModelContextProtocol.Core/Server/McpServerToolAttribute.cs); [identity.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/identity/identity.md)). Foundry agents get `require_approval: always` on every state-changing tool. Every action is audited, and anything unconfirmed fails closed. As defense in depth, the home edge should execute only commands signed by the Azure core. That last point is a design recommendation, not a sourced practice.

## Israel can link a private app, but no gate opens Ring Alarm

Ring's developer docs gate on four separate things, and they disagree with each other.

**The developer.** There is no country gate. The developer must upload "a valid, unexpired government-issued ID", and "make sure the ID type and issuing country you select match" ([Get Started](https://developer.amazon.com/docs/ring/get-started.html)). The agreement expects non-US developers: it says how someone who is not "a permanent U.S. resident or citizen" performs services ([Ring Appstore Schedule](https://developer.amazon.com/docs/ring/ring-appstore-schedule.html)).

**The Ring account.** Private apps are "Available to Ring accounts from any country", capped at **10 accounts** ([Publish](https://developer.amazon.com/docs/ring/publish.html)). A July 21, 2026 release note still says "up to 5", and nobody has corrected it ([Release Notes](https://developer.amazon.com/docs/ring/release-notes.html)). Public apps are US-only unless Ring approves otherwise "in writing" ([Program Requirements](https://developer.amazon.com/docs/ring/program-requirements.html)).

**The devices.** "Currently we only support devices located in the US" appears under the Testing Process heading, which belongs to the public-app staging flow that private apps skip ([Develop](https://developer.amazon.com/docs/ring/develop.html)). The docs never say whether the rule binds private apps, or what "located" means. The Locations API returns ISO country codes, with CA and GB in its examples and a GDPR branch for GB, DE and FR in sample code ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). That weakly suggests non-US devices can appear. It is an inference from sample code, not a commitment.

**The end user's browser.** "The Ring Appstore is only reachable from locations within the US. Users outside of the US are forwarded to the Ring top page" ([Developer FAQ](https://developer.amazon.com/docs/ring/developer-faq.html)). A private app's initial Connect step runs from the Developer Portal, not the Appstore ([Publish](https://developer.amazon.com/docs/ring/publish.html)), so first linking from Israel is plausible. Later device-selection changes are another matter. They happen only in the Appstore's My Apps page, and "Partners have no API to change a user's device access" ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). An Israeli user therefore may be unable to change device access after linking. No source resolves this.

**Hosting in Azure US changes none of these gates.** No gate keys on the caller's IP country. Ring even classes "Moving between regions or hosts" as an infrastructure change that needs no re-certification ([Certify](https://developer.amazon.com/docs/ring/certify.html)). The only effect of cloud hosting is the documented WAF rule: register a static egress IP with Ring developer support or expect 406s ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). US hosting therefore buys nothing, and a region near Israel serves the user better. Reaching the Appstore through a US VPN is not a design option either. Ring "may rely on our determination of an end user's geographic regions for all purposes" ([Ring Appstore Schedule](https://developer.amazon.com/docs/ring/ring-appstore-schedule.html)), and partners must not "circumvent, or avoid any security device, mechanism, or protocol" ([Program Requirements](https://developer.amazon.com/docs/ring/program-requirements.html)).

Even full eligibility would not remove the home edge, because **the official API has no Ring Alarm surface**. The scopes cover cameras and doorbells as a whole, Early Access sensors (contact, flood/freeze, temperature/humidity, air quality) and Chimes. No base station, keypad, alarm motion sensor or siren appears among them ([Configure](https://developer.amazon.com/docs/ring/configure.html)). Device capabilities "are read-only", and the only actuation is Chime sound playback ([Developer FAQ](https://developer.amazon.com/docs/ring/developer-faq.html); [API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). Video is under its own pressure. TAKE encryption is rolling out "as the default end-to-end encryption" worldwide ([Amazon Developer Community Dev News](https://community.amazondeveloper.com/t/dev-news-aug-31-26-hackathon-ring-updates/29048)). During the rollout, a TAKE device stays visible, but "video requests return encrypted content", while E2EE devices "are not returned by any Ring Partner API" ([Developer FAQ](https://developer.amazon.com/docs/ring/developer-faq.html)). Every connected account also needs a paid plan or trial, which the user's Ring Multi satisfies, and all media carries an unremovable watermark ([Release Notes](https://developer.amazon.com/docs/ring/release-notes.html)).

Where the official path works, it fits the Azure half of the architecture better than anything else. It needs public HTTPS Account Link and Token Exchange endpoints. The Token Exchange code expires in 60 seconds, and "Ring doesn't retry". Webhooks must be acknowledged within 5 seconds ([Release Notes](https://developer.amazon.com/docs/ring/release-notes.html); [API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). Those are jobs for an always-on cloud host with an allowlisted IP, not a home box. Its **RTSPS** live view also needs no WebRTC stack at all: ffmpeg reads it directly. That sidesteps the SIPSorcery problem and keeps a camera-only path pure .NET plus ffmpeg. "There is no official Ring Partner SDK", so the client is hand-rolled `HttpClient` code with the required `User-Agent` and `Hardware_Id` headers ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)). For open-source distribution, the only clean model is "bring your own private app", because partners may not "provide your developer credentials to any third party" ([Program Requirements](https://developer.amazon.com/docs/ring/program-requirements.html)).

The question is cheap to settle by test, in about one to three days. Pass ID verification, then create a private app with **working** Token Exchange and Account Link handlers; placeholder URLs fail, so adapt [ring-api-helloworld](https://github.com/AmazonAppDev/ring-api-helloworld). Connect the Israeli account from the Developer Portal. From a residential IP, call `GET /v1/devices?include=location,configurations` and attempt one RTSPS frame grab, then repeat the call from Azure. Read the results this way. A linking failure is a handler bug, not evidence about geography. A 406 is the WAF. An empty device list means the US-device gate binds private apps, and the official path is closed for Israel. Devices with `country: "IL"` but unreadable video means TAKE. A watermarked JPEG means the path is viable.

## Deliver one fresh JPEG by default; treat live view as an action

MCP cannot carry video. The 2026-07-28 schema's `ContentBlock` is text, image, audio, `resource_link` or embedded resource ([schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/schema/2026-07-28/schema.ts#L2305-L2306)). Claude's vision accepts JPEG, PNG, GIF and WebP, and for an animation "only the first frame is used" ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). "Live video to an agent" therefore means frames, and video is for humans. How to get a genuinely current frame depends on which Ring API produced it.

| | Official Partner API | Unofficial (`ring-client-api` family) |
|---|---|---|
| Live transport | WHEP (WebRTC) or RTSPS over TCP | WebRTC via Ring's `live_view` signaling websocket |
| Session cap | 30 s on battery, 60 s on line power; reconnecting is sanctioned | About 10 min (community observation) |
| On-demand still | None. Frames come from stored media only | Wired cameras: forced `snapshots/next`, at most about 10 s old. Battery cameras: about a 10-min cadence |
| "Current frame" recipe | RTSPS into `ffmpeg -frames:v 1` | Open a live session, drain the start-up backlog, convert the newest keyframe to JPEG |
| WebRTC stack needed | No (RTSPS) | Yes: werift (Node) or pion (Go). SIPSorcery is barred in Israel |
| Side effects | Mandatory watermark; triggers a recording | `on_demand` recording; motion alerts suppressed; battery drain |
| Encryption | TAKE: video encrypted. E2EE: device hidden | E2EE disables third-party integrations; TAKE's effect undocumented |

The unofficial live-view protocol is stable and well understood. A REST ticket opens a websocket to Ring's signaling host. The client sends `live_view` with an SDP offer, follows with `activate_session`, which is required "to keep the stream alive longer than 70 seconds", and pings every five seconds ([webrtc-connection.ts](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/streaming/webrtc-connection.ts)). Three independent implementations match it: TypeScript, go2rtc's Go and ringstream's Go ([go2rtc ws.go](https://github.com/AlexxIT/go2rtc/blob/c245815e75e2a5fd60b4290f12bfc04e55a984d3/pkg/ring/ws.go#L115)). Porting the signaling is easy; the media stack is the hard part.

Every live view has side effects on the user's Multi plan. With a Protect-tier plan, "all 'live streams' are actually recording sessions as well" ([ring-mqtt FAQ](https://github.com/tsightler/ring-mqtt/wiki/Frequently-Asked-Questions-(FAQ))). "Ring cameras will not send motion notifications while live streaming is active" ([ring-mqtt wiki: Video Streaming](https://github.com/tsightler/ring-mqtt/wiki/Video-Streaming)). Battery drains, too. A naive frame grab is also stale: "Ring hands over a backlog when a session opens — several seconds of it on a doorbell". A frame grabber must drain to the newest keyframe and send a Picture Loss Indication at start-up rather than wait on Ring's "~2-second cadence" ([ringstream README](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/ringstream/README.md)).

Freshness splits on power mode, so `get_current_image` must branch on `power_mode`, not on the model name ([ring-camera.ts L127-L129](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-camera.ts#L127-L129)). **Wired cameras**, such as the user's two floodlights, get a forced `app-snaps.ring.com/snapshots/next/{id}?extras=force` request ([ring-camera.ts L620-L652](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-camera.ts#L620-L652)). The image is no more than about 10 seconds old, per a 2020 wiki page that may be dated ([dgreif wiki: Snapshot Limitations](https://github.com/dgreif/ring/wiki/Snapshot-Limitations)). No stream opens, so there is no recording and no motion blindness. **Battery cameras**, the Video Doorbell 4 and Battery Doorbell 2K Plus, are slower. They "only refresh timestamp every 10 minutes", and they cannot snapshot while recording ([ring-camera.ts L529-L533](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-camera.ts#L529-L533); [ring-camera.ts L295-L306](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-camera.ts#L295-L306)). They should return the newest cached or push-notification image with an explicit `age_seconds`. A `fresh=true` option opens a short session, grabs one frame and closes the session. The Stick Up Cam ships in battery, plug-in and solar variants, so its class must be read from the device rather than assumed.

The community's battery guardrails converge, and the bridge should copy them. Scrypted warns that a persistent stream "will drain the battery faster than it can charge", and it auto-stops sessions after two minutes unless they are refreshed ([Scrypted Ring README](https://github.com/koush/scrypted/blob/78320e94ad977a77fa2bb201346b98630b8b1d47/plugins/ring/README.md)). ring-mqtt disables interval snapshots on battery cameras by default ([ring-mqtt camera.js](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/devices/camera.js#L400-L420)). The bridge's version is a per-camera cooldown on fresh frames, a hard session cap of 60–120 seconds, and never a background or prebuffer stream. Concurrent frame requests share one session, and `battery_level` and `power_mode` go out in every result. No source measures time-to-first-frame or battery cost per live view, so log both from day one.

On the official API, the current frame comes only from a live session. The image endpoint serves stored media through `at_timestamp` or `latest_in_range`, within a 24-hour window. Live view is reachable over `rtsps://video.rtsp.amazonvision.com:322/v1/devices/<id>/stream`. Pass the token, about 1,300 characters long, as `?token=`, because FFmpeg truncates it in URL user-info. Check `e2e_encryption` before trying ([API Documentation](https://developer.amazon.com/docs/ring/api-documentation.html)).

| Option | Agent sees it | Human sees it | Cost or limit | Verdict |
|---|---|---|---|---|
| (a) One JPEG image block plus metadata | Yes | Usually inline | 640×360 ≈ 299 tokens; 1280×720 ≈ 1,196; 1080p 1,560–2,691 | **Default** |
| (b) Burst of 5–8 downscaled frames | Yes, as separate images | Yes | 5 × 640×360 ≈ 1.5k tokens; 20 images per claude.ai message | Motion and sequence questions |
| (c) Short MP4 as `resource_link` or embedded blob | No | Only if the client or an App plays it | A few MB per 10 s, plus about 33% for base64 | Humans and audit; pair with (b) |
| (d) Raw HLS, WebRTC or RTSP URL | No | Only through an external URL or App CSP | Bandwidth | Avoid |
| (e) MCP Apps viewer | Only through tool results | claude.ai web, ChatGPT, VS Code, Goose | Medium build effort | Best live experience |

The token figures follow Claude's `⌈width/28⌉ × ⌈height/28⌉` formula, which makes **downscaling to about 1024 pixels on the long edge** the cheapest single optimization ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). For humans, the strongest design keeps media inside the authenticated MCP channel, and it can grow in three stages. In the first, an MCP App polls an app-only `get_live_frame(handle)` tool at one to two frames per second. Such a tool is hidden from the agent but "callable by apps via `tools/call`", and its JPEGs render under the default CSP of `img-src 'self' data:` with `connect-src 'none'` ([MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/266a9e3b70dbd4a4f0546dda95da2a2c1a8be4b7/specification/2026-01-26/apps.mdx)). In the second, the App plays a short MP4 fetched through `resources/read`, following the official video example ([video-resource-server](https://github.com/modelcontextprotocol/ext-apps/blob/266a9e3b70dbd4a4f0546dda95da2a2c1a8be4b7/examples/video-resource-server/README.md)). Only in a third stage, if ever, comes real HLS or WebRTC with declared domains.

Because 2026-07-28 removed protocol sessions, live state rides on "explicit, server-minted handles passed as ordinary tool arguments". `start_live_view` returns a handle with a time-to-live, and `stop_live_view` revokes it ([2026-07-28 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/docs/specification/2026-07-28/changelog.mdx)). Annotate `start_live_view` as destructive and non-idempotent, so hosts prompt for approval. Rate-limit and audit it; Ring's own `on_demand` entries add a household-visible trail.

Three privacy controls apply on top. Media sidecars must bind to localhost with credentials, because both go2rtc and ringstream ship unauthenticated defaults ([go2rtc API README](https://github.com/AlexxIT/go2rtc/blob/c245815e75e2a5fd60b4290f12bfc04e55a984d3/internal/api/README.md); [ringstream session.go](https://github.com/tsightler/ring-mqtt/blob/996be5b73537d845f9176eef6efcf5ed055be85e/ringstream/session.go#L123-L125)). Camera frames are untrusted input: text held up to a doorbell is a demonstrated visual prompt-injection vector ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-image-prompt-injection-multimodal-llm-2026/)). And the bridge should never promise face identification, because Claude "cannot be used to name people in images" ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)).

Four unknowns decide parts of this design, and none has a source. The first is app polling: if claude.ai or ChatGPT throttle, or prompt approval for, app-initiated `tools/call`, the polling viewer fails and the MP4 pattern becomes the first version. The second is Claude Desktop rendering. The connector docs list MCP Apps only for claude.ai web, while the ext-apps quickstart says they render in Claude Desktop ([Get started with connectors](https://claude.com/docs/connectors); [ext-apps quickstart](https://github.com/modelcontextprotocol/ext-apps/blob/266a9e3b70dbd4a4f0546dda95da2a2c1a8be4b7/docs/quickstart.md)). The third is whether claude.ai's roughly 150,000-character tool-result cap counts base64 image data; keeping JPEGs near 100 KB avoids the question. The fourth is TAKE on the unofficial path. The user's E2EE is off, but nothing found documents what TAKE does to the community WebRTC path, or whether a camera can be taken off TAKE. Check each camera's encryption status before building on video.

## Conclusion

The research turns a language question into a placement question. The stable, standards-driven half of the system is the MCP server, OAuth, policy, event log and per-client push adapters. It has a first-class C# SDK and belongs in Azure, where every client can reach it. The volatile half is everything that talks to Ring. It breaks about once a year, gets fixed first in JavaScript, and is tolerated only from residential IPs, so it belongs at home in whatever language its maintainers use, behind a contract thin enough to swap. Each Ring backend lands where Ring permits it: the unofficial path on the home IP, and the official Partner API in Azure with an allowlisted address. Being in Israel surfaces in places no one would look for it: a WebRTC license clause, an ambiguous device-location rule, 12-hour session churn for non-US accounts, and a Foundry region list without Israel Central. Each forced a different component choice.

Three cheap experiments should precede any build, and each decides one component. The first is a one-to-three-day private-app link with the Israeli account, run from a residential IP and then from Azure. It decides whether a sanctioned camera path exists, and whether that path can run in the cloud behind an allowlisted IP. The second is a spike on the user's actual doorbells and floodlights: time-to-first-frame, TAKE status and battery cost. It sets the live-view guardrails and shows whether video is readable at all. The third tests the pinned C# channel shim against Claude Code, and decides whether the Claude Code push adapter can stay in .NET. None of the three can move the unofficial path into Azure, because a passing Azure probe measures only today's reputation score. If the private app works, the home edge shrinks to its irreducible core, Ring Alarm and device control, which stays on the unofficial path whatever the tests show.
