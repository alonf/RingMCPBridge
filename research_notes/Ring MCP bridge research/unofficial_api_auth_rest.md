## 1. Authentication flow (ring-client-api and python-ring-doorbell)

### Takeaway
Both libraries use the same legacy "password grant" flow, the one the Android app uses: `POST https://oauth.ring.com/oauth/token` with `client_id=ring_official_android`, `scope=client`, and the `password` or `refresh_token` grant. Accounts with 2FA get HTTP 412, then the client resends the request with a `2fa-code` header. After that the client registers a "device" via `POST https://api.ring.com/clients_api/session`, keyed by a stable `hardware_id`. Refresh tokens rotate and must be saved after every refresh. Since Feb 2026 a growing number of users get Cloudflare-WAF `406` responses on the legacy endpoint. A maintainer-authored OAuth 2.0 + PKCE replacement (the `/oauth/v2/*` web flow) is still in an open PR and has not been merged.

### Cited Findings

**Token endpoint, client_id, grants (TS) [code]**
- `getAuth()` POSTs JSON to `https://oauth.ring.com/oauth/token` with body `{client_id: 'ring_official_android', scope: 'client', ...grantData}` and headers `'2fa-support': 'true'`, `'2fa-code': <code or ''>`, `hardware_id: <hwid>`, `'User-Agent': 'android:com.ringapp'`. The library adds `Content-Type: application/json` and `Accept: application/json` to every JSON request. — [T/rest-client.ts L321-L340](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L321-L340), [L112-L123](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L112-L123)
- Grant selection: if a stored refresh token exists and no 2FA code is being submitted, it sends `{grant_type:'refresh_token', refresh_token}`. Otherwise it sends `{grant_type:'password', username, password}`. If it has neither, it throws "Refresh token is not valid… See wiki/Refresh-Tokens". — [T/rest-client.ts L299-L319](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L299-L319)
- Token response type: `{access_token, expires_in, refresh_token, scope:'client', token_type:'Bearer'}`. — [T/ring-types.ts L1149-L1155](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-types.ts#L1149-L1155)
- Access-token lifetime handling: the cached auth promise is cleared 60 s before `expires_in`, and the code assumes 3600 s when `expires_in` is missing. — [T/rest-client.ts L250-L274](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L250-L274)

**Token endpoint (Python) [code]**
- Constants: `ENDPOINT = "https://oauth.ring.com/oauth/token"`, `CLIENT_ID = "ring_official_android"`, `SCOPE = ["client"]`. — [P/const.py L12-L17](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/const.py#L12-L17)
- Python's wire format differs from TS. It uses oauthlib `LegacyApplicationClient` to build a **form-urlencoded** body with `include_client_id=True` and also sends HTTP Basic auth `BasicAuth(CLIENT_ID, "")`. The initial fetch sends `User-Agent: <caller-supplied>` and `hardware_id`. The `2fa-support: true` and `2fa-code` headers are only added when an `otp_code` is passed. — [P/auth.py L65-L118](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L65-L118)
- Python's refresh request (`async_refresh_tokens`) sends only `Accept: application/json` and `Content-Type: application/x-www-form-urlencoded;charset=UTF-8` plus Basic auth. It sends **no User-Agent and no hardware_id header** on refresh. — [P/auth.py L120-L145](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L120-L145)
- Sept 2024 break: "The ring oath endpoint now requires the `client_id` to be sent with initial token request. This change means all prior versions of this library will no longer work" (PR #446, merged 2024-09-26, released as 0.9.6). — [PR #446](https://github.com/python-ring-doorbell/python-ring-doorbell/pull/446); [0.9.6 release summary #447](https://github.com/python-ring-doorbell/python-ring-doorbell/issues/447)

**2FA / MFA [code]**
- TS: HTTP **412** means a 2FA code is needed. HTTP **400** with an `error` starting "Verification Code" means an invalid code. The 412 body is `{next_time_in_secs, phone, tsv_state}` with `tsv_state ∈ 'sms' | 'email' | 'totp'`. For `totp` the prompt reads "from your authenticator app", otherwise "sent to {phone} via {tsv_state}". — [T/rest-client.ts L383-L411](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L383-L411); [T/ring-types.ts L1157-L1168](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-types.ts#L1157-L1168)
- TS: `error_description === 'too many requests from dependency service'` is reported as "Ring limits 2fa to 10 codes within 10 minutes. Please try again in 10 minutes." — [T/rest-client.ts L413-L427](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L413-L427)
- Python: the first call omits the 2FA headers. The 412 response has no token, so oauthlib raises `MissingTokenError`, which the library maps to `Requires2FAError`. The caller then calls `async_fetch_token(username, password, otp_code)`. — [P/auth.py L78-L118](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L78-L118); README example: [README.rst](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/README.rst)
- Wiki: "Ring now requires the use of Two-Factor Auth (2fa) for all accounts. If you have not turned on text-based 2fa, you will receive a verification code via email instead." — [dgreif wiki: Refresh-Tokens](https://github.com/dgreif/ring/wiki/Refresh-Tokens)

**hardware_id and session/device registration [code]**
- TS hardware_id: a UUIDv5 of the OS system UUID (from `systeminformation`) under namespace `e53ffdc0-e91d-4ce1-bec2-df939d94739d`. It can also be derived from the `systemId` option, and falls back to a random UUIDv4 on a 5 s timeout or when no system UUID exists. — [T/util.ts L73-L98](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/util.ts#L73-L98)
- Python hardware_id: `uuid5(UUID("379378b0-f747-4b67-a10f-3b13327e8879"), str(uuid.getnode()) + user_agent)` (MAC address plus UA) unless the caller supplies one. The comment says this prevents "multiple auth entries in ring.com". `device_model = "ring-doorbell:" + user_agent`. — [P/auth.py L50-L60](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L50-L60); [P/const.py L73](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/const.py#L73)
- Session creation (TS): `POST https://api.ring.com/clients_api/session` with `Authorization: Bearer <access_token>` and body `{device: {hardware_id, metadata: {api_version: 11, device_model: controlCenterDisplayName ?? 'ring-client-api'}, os: 'android'}}`. A code comment says the `os` value "can use android, ios, ring-site, windows". The response is a `ProfileResponse` (profile id, email, `authentication_token`, `hardware_id`, `tfa_enabled`, features…). — [T/rest-client.ts L431-L446](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L431-L446); [T/ring-types.ts ProfileResponse/SessionResponse](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/ring-types.ts)
- Session creation (Python): the same endpoint with `{"device": {"hardware_id", "metadata": {"api_version": "11", "device_model": "ring-doorbell:<UA>"}, "os": "android"}}`. — [P/ring.py L78-L96](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/ring.py#L78-L96)
- TS re-creates the session **every 12 hours**. The code comment gives the reason: "needed to keep the session alive for users outside the US, due to Data Residency laws… Ring is clearing the session info after ~24 hours, which breaks Push Notifications". — [T/rest-client.ts L486-L503](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L486-L503)
- Every authenticated TS REST call sends `authorization: Bearer …`, `hardware_id`, and `User-Agent: android:com.ringapp`. — [T/rest-client.ts L505-L524](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L505-L524). Python has sent `hardware_id` on all requests since 0.9.8 (PR #455, Oct 2024). — [P/auth.py L202](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L202); [CHANGELOG 0.9.8](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/CHANGELOG.md)

**Refresh token rotation and persistence**
- TS wraps Ring's refresh token. The string the library exposes is `base64(JSON{rt, hid, pnc})`, i.e. the Ring refresh token plus the hardware ID plus the FCM push credentials. `parseAuthConfig` still accepts a raw Ring token. — [T/rest-client.ts L213-L239](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L213-L239). Introduced in 11.8.0: "Embed hardware id in the refresh token string. This should prevent a second device from being created in Ring Control Center" and "Embed push notification credentials in the refresh token". — [T/CHANGELOG 11.8.0](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/CHANGELOG.md)
- Every successful `getAuth` emits `onRefreshTokenUpdated.next({oldRefreshToken, newRefreshToken})`, which is an rxjs `ReplaySubject(1)` surfaced as `RingApi.onRefreshTokenUpdated`. A change to the push credentials also emits it. — [T/rest-client.ts L343-L355, L608-L640](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L343-L355); [T/api.ts L60-L65](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/api.ts#L60-L65)

Consumers of the ring-client-api library **MUST** subscribe to `api.onRefreshTokenUpdated`". Re-using the original token "will generally work for authentication" but breaks push notifications permanently. The only fix then is to delete the client in Control Center and re-auth, because Ring "only accepts [FCM registration] during initial device registration". — [dgreif wiki: Refresh-Tokens](https://github.com/dgreif/ring/wiki/Refresh-Tokens)

**Failure modes**
- TS 401 handling: `request()` responds to a 401 by calling `refreshAuth()` and then recursively retries `this.request(options)` with **no retry cap**. — [T/rest-client.ts L525-L531](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L525-L531) [code]
- TS refresh failure: if the refresh-token grant fails for **any** reason, the client clears the refresh token and auth config and calls `getAuth()` again. That falls back to email/password if configured, otherwise it throws "Refresh token is not valid". — [T/rest-client.ts L362-L369](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L362-L369) [code]. Open PR #1704 (2026-02-01) says this causes "permanent authentication failures after temporary Ring service disruptions". It proposes clearing the token only on 401 with `invalid_grant`/`access_denied`. — [PR #1704](https://github.com/dgreif/ring/pull/1704). Related open issues: [#1071 "API does not recover from temporary refresh token failure" (2022)](https://github.com/dgreif/ring/issues/1071), [#1252 "Infinite loop in getAuth" (2023)](https://github.com/dgreif/ring/issues/1252).
- Python 401 handling: on 401 it refreshes the tokens (and calls `token_updater`), but `raise_for_status` still raises `RingError` for the original request. **The request is not retried.** Proactive refresh happens only when oauthlib detects local expiry (`TokenExpiredError`). — [P/auth.py L208-L256](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L208-L256) [code]
- 406 / IP blocks [maintainer]: "The 406 error generally means that your IP has been blocked. Usually this is caused by use of VPN or running the code in some service where Ring has banned entire IP blocks. However, Ring also sometimes temporarily blocks IPs based on… lots of connections for different accounts from the same IP, multiple attempts to request tokens too frequently, or access using an invalid token being attempted over and over. These blocks are generally temporary, if you stop all connections for 24 hours and try again it is usually fine." — [tsightler in #1580 (2025-01-30)](https://github.com/dgreif/ring/issues/1580)
- 2026 406 wave [forum + maintainer]: users reported that from about 2026-02-23 all auth attempts returned `406` with `server: cloudflare`, `content-type: text/plain`. Workarounds reported: a full versioned app UA (tsightler), a reinstalled OS ([#1715](https://github.com/dgreif/ring/issues/1715)), downgrading **Node 26 → 24** ("this just doesn't work with node 26", #1715 comment 2026-06-09, unverified), and regenerating the hardware ID (HomeSeer plugin author, #1717, speculative). — [#1717](https://github.com/dgreif/ring/issues/1717), [#1715](https://github.com/dgreif/ring/issues/1715)
- A non-JSON 406 body used to crash `getAuth` with a `TypeError` ("Cannot use 'in' operator…"). This is fixed on main in PR #1818 (2026-08-24) but **unreleased** (pending changeset `fix-non-json-oauth-error.md`). — [PR #1818](https://github.com/dgreif/ring/pull/1818); [issue #1817](https://github.com/dgreif/ring/issues/1817)
- "Authorized Client Devices" [wiki]: each client appears in Ring app → Control Center → Authorized Client Devices. Library-created entries show as `android` devices. "Ring seems to have a limitation on the number of devices which can be registered to receive Push Notifications", and some setups add a new device registration on every start. The fix is to remove the extras and generate a new refresh token. — [wiki: Notification-Troubleshooting](https://github.com/dgreif/ring/wiki/Notification-Troubleshooting). `controlCenterDisplayName` sets the display name (TS option). — [T/README.md options table](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/README.md)
- Push transport: FCM needs a persistent connection to `mtalk.google.com:5228`. Ad-blocking DNS or DoH can break it. — [wiki: Notification-Troubleshooting](https://github.com/dgreif/ring/wiki/Notification-Troubleshooting). An open issue from 2026-09 reports `PHONE_REGISTRATION_ERROR` during FCM registration. — [#1826](https://github.com/dgreif/ring/issues/1826)

**New OAuth 2.0 + PKCE flow (unmerged) [maintainer + code in fork]**
- The web/app "modern" login uses `GET oauth.ring.com/oauth/v2/authorize` → `GET/POST /oauth/v2/signin` (form, `csrf-token` scraped from the HTML) → `POST /oauth/v2/2fa/verify` → `GET /oauth/v2/authorize` (302 with `code`) → callback `https://ring.com/signin/callback` → `POST /oauth/token`. The app still offers a legacy "Having trouble? Sign in here" path that uses the old endpoint. tsightler: "That doesn't mean we should not update to the new auth methods of course, no telling when the old ones might go away." — [#1717 (2026-03-06 … 2026-05-08)](https://github.com/dgreif/ring/issues/1717)
- PR #1750 "Implement OAuth 2.0 + PKCE authentication flow" by tsightler is **open** (created 2026-05-25, updated 2026-08-25). It says Ring "has tightened the security around the legacy API endpoint", and that the new flow "is more fragile… could be impacted by changes to the Ring auth web page". — [PR #1750](https://github.com/dgreif/ring/pull/1750)
- Fork implementation (`tsightler/ring@v3_and_oauth`): it sends `client_id=ring_official_android`, `redirect_uri=https://ring.com/signin/callback`, `code_challenge` with `code_challenge_method=S256`, follows redirects manually with a cookie jar, and exchanges `grant_type=authorization_code` + `code_verifier` at `/oauth/token`. Refresh still uses `grant_type=refresh_token` at `/oauth/token`, and the UA is still `android:com.ringapp`. — [tsightler/ring v3_and_oauth rest-client.ts](https://github.com/tsightler/ring/blob/v3_and_oauth/packages/ring-client-api/rest-client.ts) (lines ≈450-790)

### Inferences
- An MCP Ring client must treat the refresh token as **mutable state**. It should save the token atomically on every `onRefreshTokenUpdated` / `token_updater` callback, and only one live process should use a given token. If two processes share one token, the rotation will invalidate one of them. This inference rests on the rotation evidence above, not on a documented Ring rule.
- Keep the `hardware_id` stable and persist it next to the token. TS does this automatically inside the wrapped token. In Python you must pass `hardware_id=` yourself if the host's MAC/UA can change, e.g. in containers. Otherwise each restart can add a new entry to "Authorized Client Devices".
- The legacy `oauth/token` password grant is the main fragility risk for 2026–2027. Ring has not removed it, but Cloudflare-WAF filtering is tightening. A new integration should plan an abstraction that can switch to the PKCE flow (PR #1750) and a full app-like UA. It should also not retry failed auth in a tight loop, since that makes IP blocks worse.
- Neither library's 401 behaviour is ideal for a server. TS can loop with no cap, and Python fails the in-flight call. An MCP wrapper should add its own bounded retry and circuit breaker around auth.

### Gaps
- I found no authoritative value for the access-token `expires_in` that Ring returns. The code assumes 3600 s when it is missing, and the wiki says tokens rotate "typically every hour". I also found no exact refresh-token TTL or grace period ("expire shortly after use" is all the README says).
- The exact header set and the versioned UA string tsightler used in ring-mqtt 5.9.3 were not retrieved (the dev-branch diff was not located).
- I found no documented numeric limit on Authorized Client Devices or push registrations ("seems to have a limitation" only).

## 2. REST endpoints (hosts, discovery, metadata, history, media, settings)

### Takeaway
Most calls go to `https://api.ring.com` under `/clients_api/`, `/devices/v1/`, `/commands/v1/`, `/groups/v1/`, `/recordings/` and `/integrations/`. Location modes, alarm/websocket tickets and the streaming ticket go to `https://prd-api-us.prd.rings.solutions/api/v1/` (the "app API"). Snapshots in TS come from `https://app-snaps.ring.com`. The two libraries differ on history: TS uses `clients_api/locations/{loc}/devices/{id}/events` with a `pagination_key`, and Python uses the older `clients_api/doorbots/{id}/history?older_than=`. Ring is moving discovery and events to `device_info/v3`, `location_info/v3` and `evm/v3`. The legacy endpoints return empty or 404 results for some shared-location accounts. That migration exists only in open PRs.

- [maintainer] "the old v1 locations API returns no sites, but the v3 API does. Same with devices for shared locations… for a small number of users, only the v3 API returns the location devices." — [#1717 comment 2026-05-08](https://github.com/dgreif/ring/issues/1717)
- [forum, detailed test] On a shared/secondary account (2026-07/09), `clients_api/ring_devices` returned all arrays empty and `clients_api/locations/{id}/events` returned `{"events": []}`. `device_info/v3/devices` worked "with the existing refresh-token auth (no OAuth/PKCE … needed)". The v3 records lack `battery_life`, `subscribed`, `subscribed_motions` and the health fields, `owned` is false for everything, and legacy `doorbots/{id}/health` returns 404 for those devices. — [modert comment on PR #1749, 2026-09-29](https://github.com/dgreif/ring/pull/1749)

### Inferences
- For an MCP server, the TS library covers far more surface: location modes, alarm/websocket, `snapshots/next`, the newer events endpoint with cursor pagination, video search, and periodic footage. Python covers devices, health, `doorbots/{id}/history`, recordings, the older snapshot method, lights, siren, chime and intercom. It has no modes and no alarm support.
- Shared or secondary Ring accounts are a known blind spot for both released libraries in 2026. If the MCP server must support them, plan to call `device_info/v3/devices` and `evm/v3/history/devices` directly, or vendor tsightler's branch.
- Recording URLs (`share/play`) are short-lived signed links, and downloads need a Bearer token. An MCP tool should return or stream the media on demand rather than caching URLs. The TTL itself is unverified.

### Gaps
- I found no formal documentation of the request/response schemas for `evm/v3`, `device_info/v3` or `location_info/v3` beyond the fork code and one user report.
- I could not confirm whether Python's `doorbots/{id}/history` and TS's `locations/{loc}/devices/{id}/events` return identical event sets, or which one the current Ring app uses.
- I did not verify the TTL of the signed `share/play` URLs.
- I did not determine whether `clients_api/dings/active` still returns live data. TS stopped using it in 2022 and Python still polls it.

## 4. Rate limiting, polling and back-off

### Takeaway
Ring publishes no rate limits. What is known comes from library code and maintainer reports. Session creation can return 429 with `Retry-After`. 2FA codes are capped at 10 per 10 minutes. Abusive patterns get the IP blocked at the Cloudflare WAF (406), usually for about 24 h. The libraries poll devices only on opt-in (TS) or once a minute (Home Assistant) and use push (FCM) for events.

### Cited Findings
- TS 429 handling exists only in `getSession()`. It waits `Retry-After` seconds, or **200 s** if the header is absent, plus 1 s, then retries. — [T/rest-client.ts L462-L475](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L462-L475) [code]
- Other TS retry rules: 504 → wait 5 s and retry. 404 with Ring error codes `7050 NO_ASSET`, `7019 ASSET_OFFLINE`, `7061 ASSET_CELL_BACKUP`, `7062 UPDATING`, `7063 MAINTENANCE` → wait 20 s and retry. 404 whose body mentions the hardware_id ("Session hardware_id not found") → create a new session and retry. Network errors with no response → retry every 5 s **without limit**. All of these retries are unbounded. — [T/rest-client.ts L46-L52, L174-L195, L533-L583](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L533-L583) [code]
- TS HTTP client: an undici Agent with `connections: 6`, `pipelining: 1`, `keepAliveTimeout: 115000`, and a default 20 s timeout. — [T/rest-client.ts L36-L45](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L36-L45) [code]
- Python: 10 s default timeout (120 s for video). It has **no 429 or back-off handling**; non-2xx responses become `RingError`. — [P/const.py L55-L63](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/const.py#L55-L63); [P/auth.py L248-L256](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/auth.py#L248-L256) [code]
- Polling options (TS): `cameraStatusPollingSeconds` defaults to **no polling** ("light/siren/volume/snooze status do not update in real time and need to be requested periodically"). The README example uses 20. The implementation re-fetches `ring_devices` debounced by N seconds after each response, throttled to 500 ms. `locationModePollingSeconds` also defaults to off and "is automatically disabled for locations equipped with a Ring Alarm". — [T/README.md options](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/README.md); [T/api.ts L150-L232](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/api.ts#L150-L232); [T/location.ts L195-L198](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/location.ts#L195-L198)
- Home Assistant (python-ring-doorbell): `SCAN_INTERVAL = timedelta(minutes=1)`. On the first refresh the coordinator calls `async_update_data` (ring_devices + dings/active + groups). On later refreshes it calls `async_update_devices` plus, per device, `async_history(limit=10)` (if the device has the capability) and `async_update_health_data`. In other words, one `ring_devices` call plus about 2 calls per device every minute, with real-time events via `RingEventListener` (FCM). HA pins `ring-doorbell==0.9.14`, with `iot_class: cloud_polling`. — [HA ring/const.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ring/const.py); [HA ring/coordinator.py L94-L144](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ring/coordinator.py); [HA ring/manifest.json](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ring/manifest.json); [P/ring.py L56-L68](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/ring.py#L56-L68)
- Polling-based ding detection was removed in TS v10.0.0 (2022-05-08): "The `cameraDingsPollingSeconds` option has been removed. Ding events will now be received via push notifications". — [T/CHANGELOG 10.0.0](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/CHANGELOG.md). Python's real-time events come from `RingEventListener` over FCM. The listener was rewritten for the FCM HTTP v1 API in 0.9.2 (2024-08-29), and its event `expires_in` default is 180 s. — [P CHANGELOG 0.9.2](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/CHANGELOG.md); [P/const.py L75](https://github.com/python-ring-doorbell/python-ring-doorbell/blob/486193a80e7c924a0ab14b04d47305e1b36e419e/ring_doorbell/const.py#L75)
- 2FA limit: "Ring limits 2fa to 10 codes within 10 minutes" (TS error text). — [T/rest-client.ts L417-L424](https://github.com/dgreif/ring/blob/925a3aa29a8b2ac8aa491d0eb045e520db079b33/packages/ring-client-api/rest-client.ts#L417-L424)
- IP blocking (406) causes and recovery: see §1. tsightler says blocks are triggered by VPNs, many accounts from one IP, frequent token requests, or repeated invalid-token use, and usually clear after 24 h without connections. — [#1580](https://github.com/dgreif/ring/issues/1580)
- [forum] A Python user who rate-limits clip downloads and avoids parallel requests says that "in the past would get my IP Banned". — [python-ring-doorbell #483](https://github.com/python-ring-doorbell/python-ring-doorbell/issues/483)

### Inferences
- A safe MCP default: cache `ring_devices`/`locations` and refresh on demand with a TTL of 30–60 s, with an optional poll no faster than about 20 s. Serialize media downloads. Never retry auth more than a handful of times; use an exponential back-off and a lockout of hours after a 406. Rely on FCM push for events instead of history polling.

### Gaps
- I found no published or measured request-per-minute thresholds for `api.ring.com`. The 200 s default and the 24 h guidance are heuristics.

### Inferences
- LGPL-3.0 allows an MCP server of any license to use python-ring-doorbell as an unmodified dynamically imported dependency. Modified copies of the library itself would have to be released under LGPL. MIT (TS) places no such constraint. This is a general reading of the licenses, not legal advice.
- Both libraries use an unofficial API in a way that impersonates the Android app (client_id `ring_official_android`). Neither repo includes any Ring authorization or ToS grant, so the access is "unofficial" in the strict sense. Ring could block it at any time, as the Cloudflare 406 wave shows.

### Gaps
- I did not review Ring's Terms of Service on automated or third-party API access. It is outside this scope and worth checking separately.
